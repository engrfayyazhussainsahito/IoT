Application-Layer Protocol Security (MQTT, CoAP, REST for devices)

Harden an MQTT broker against topic-hijacking and unauthorized publish.

35 min read Level: MS foundation → advanced Status: Full lesson

1. Introduction

Week 7 closes where most IoT data actually flows: the application-layer protocols carrying telemetry and commands between devices, gateways, and cloud platforms. Getting the access-control model right here is often more impactful than any lower-layer protocol choice.

2. Learning Outcomes

By the end of this lesson you will be able to:

  • Harden an MQTT broker against topic-hijacking and unauthorized publish.
  • Compare CoAP/DTLS with MQTT/TLS for a constrained deployment.

3. Prerequisites

Week 0 foundations, plus Weeks 0–6 of this course.

4. Core Concepts

MQTT uses a publish-subscribe model built around topics — a hierarchical string like building/floor3/room12/temperature. Security hinges entirely on topic-level ACLs (Access Control Lists): without them, any authenticated client can often publish to or subscribe to any topic, including ones belonging to other devices or tenants — a classic multi-tenant isolation failure.

CoAP (Constrained Application Protocol) is REST-like but designed for constrained devices and UDP transport, typically paired with DTLS (Week 3) for security — its RESTful design maps naturally onto resource-oriented device APIs (GET /sensor/temperature).

REST/webhook security for device callbacks: when a cloud platform calls back to a device or a third-party service (a webhook), that callback endpoint needs its own authentication — a surprisingly common gap is a webhook receiver trusting any request that "looks like" it came from the expected source, based only on network origin rather than a verified signature or token.

7. Mathematical / Formal Foundations

No formula — instead, a least-privilege topic design principle: a device should generally be granted publish rights only to its own topic namespace, and subscribe rights only where its function genuinely requires reading other devices' data — not broad wildcard access "for convenience" during development that never gets tightened before production.

8. Practical Examples

Worked example: an MQTT broker configured without topic ACLs allows any authenticated device to publish to building/+/+/lock/command (a wildcard subscription/publish pattern) — meaning any single compromised device credential can send unlock commands to every door lock in the building, not just its own. Proper per-device ACLs scoped to each device's own topic prevent this entirely.

9. Code / Worked Example

MQTT ACL CONFIGURATION EXAMPLE (Mosquitto-style syntax, illustrative)
# Device can only publish to its own topic namespace
user device_room12
topic write building/floor3/room12/#

# Monitoring app can read (but not write) across the building
user monitoring_app
topic read building/#

# Without ACLs like these, any authenticated client can typically
# publish/subscribe to ANY topic -- a common, serious misconfiguration.

10. Security Perspective

Missing topic-level ACLs are one of the most common, highest-impact IoT misconfigurations found in real assessments — the underlying transport may be perfectly encrypted via TLS while the authorization model above it is effectively absent, a classic case of confusing "encrypted" with "access-controlled."

11. Industry Perspective

Managed MQTT/IoT platform services increasingly enforce per-device topic scoping by default (tying a device's credential directly to its permitted topic namespace), reducing the chance of this misconfiguration compared to a self-hosted broker configured manually.

12. Research Perspective

Internet-wide scans of publicly exposed MQTT brokers have repeatedly found large numbers with no authentication or ACLs at all, exposing live telemetry and, in some cases, control channels for real devices — an ongoing, measurable research finding rather than a one-time historical issue.

13. Case Study

Multiple documented smart-building and smart-home platform vulnerabilities have stemmed directly from missing or overly permissive MQTT topic ACLs, allowing cross-device or cross-tenant access that the platform's designers had not intended or tested for.

14. Common Misconceptions

  • "If MQTT traffic is encrypted with TLS, it's secure." — Encryption protects data in transit; it says nothing about whether topic-level authorization is properly configured.
  • "CoAP doesn't need the same access-control attention as MQTT since it's more like a simple API." — CoAP resources need the same authorization rigor as any REST-style API; the protocol's simplicity doesn't grant automatic security.
  • "Webhook callbacks are safe if they come from a known IP address." — Network origin alone is spoofable or otherwise insufficient; callbacks should be authenticated via signatures or tokens, not just source IP.

16. Glossary

MQTT topic ACL
An access control rule restricting which MQTT topics a specific client may publish to or subscribe from.
CoAP
Constrained Application Protocol — a lightweight, REST-like protocol designed for constrained devices, typically secured with DTLS.

17. Self-Assessment

1. What is the primary risk of an MQTT broker with no topic-level ACLs configured?

Without topic-level ACLs, MQTT's default behavior often permits any authenticated client broad access across topics, breaking the isolation between different devices' or tenants' data and commands.
