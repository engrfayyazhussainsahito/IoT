Wireless/IoT Protocol Fundamentals (BLE, Zigbee/Thread, LoRaWAN, Z-Wave, NFC/RFID)

Compare range, power, and security models across common IoT radios.

40 min read Level: MS foundation → advanced Status: Full lesson

1. Introduction

Week 0 introduced networking topology in the abstract. Now we get concrete: the specific radio protocols that carry most real IoT traffic, and — crucially — what security guarantees each one actually provides versus what a product team might assume it provides.

2. Learning Outcomes

By the end of this lesson you will be able to:

  • Compare range, power, and security models across common IoT radios.
  • Match a protocol's built-in security guarantees to a deployment scenario.

3. Prerequisites

Week 0 foundations, plus Weeks 0–6 of this course.

4. Core Concepts

A quick tour, focused on security posture rather than radio physics:

  • Bluetooth Low Energy (BLE) — pairing establishes a shared key; GATT (Generic Attribute Profile) defines how services and characteristics are exposed. Security depends heavily on pairing method used ("Just Works" pairing offers essentially no protection against an active attacker; passkey or numeric comparison methods are much stronger).
  • Zigbee / Thread — mesh protocols using a network-wide key for link-layer encryption. Historically, many Zigbee deployments have used a well-known, standardized default "Trust Center link key" during commissioning, creating a brief but real interception window.
  • LoRaWAN — uses a join procedure (OTAA — Over-The-Air Activation, or the weaker ABP — Activation By Personalization) to derive session keys; OTAA is strongly preferred since ABP uses static, unrotated keys.
  • NFC/RFID — very short range by design, but vulnerable to relay attacks, where an attacker uses two colluding devices to extend the effective range, tricking a system into thinking a legitimate credential is nearby when it's actually being relayed from far away.

7. Mathematical / Formal Foundations

No formula — instead, a configuration-audit habit: for any protocol on this list, the security-relevant question is never just "does it support strong security" but "which specific mode/method is this deployment actually using." BLE, Zigbee, and LoRaWAN all support both strong and weak configurations simultaneously.

8. Practical Examples

Worked example: a smart-lock uses BLE "Just Works" pairing for ease of setup, since it requires no display or keypad on the lock itself. An attacker within radio range during the pairing window can perform a man-in-the-middle attack, since Just Works provides no authentication of the pairing process itself — a real, documented weakness class rather than a theoretical one.

10. Security Perspective

Reading "this protocol supports AES-128 encryption" in a datasheet tells you almost nothing about a specific deployment's actual security — the devil is entirely in which optional mode was chosen, and vendors frequently choose the easier, weaker option to simplify user setup experience.

11. Industry Perspective

Protocol certification bodies (Bluetooth SIG, Zigbee Alliance/CSA, LoRa Alliance) have progressively strengthened default security recommendations in newer protocol revisions, but backward compatibility requirements mean weaker legacy modes often remain supported and selectable for years.

12. Research Perspective

Academic and industry security research continues to find real-world deployments using the weakest available configuration option (Just Works pairing, ABP activation, default Zigbee keys) at surprisingly high rates, underscoring that this is a persistent deployment problem, not a solved one.

13. Case Study

Documented relay-attack research against NFC-based and RF-based vehicle entry systems has demonstrated real-world exploitation of the short-range assumption these protocols rely on, using inexpensive, commercially available relay hardware.

14. Common Misconceptions

  • "If a protocol supports AES encryption, a device using it is secure." — Support for strong encryption doesn't guarantee the deployment actually uses the strongest available mode.
  • "NFC/RFID's short range makes relay attacks impractical." — Relay attacks specifically defeat the short-range assumption using two colluding devices, and have been demonstrated repeatedly in practice.
  • "All Zigbee/Thread mesh networks are equally secure." — Security depends heavily on how network keys are provisioned during commissioning, not just the protocol's theoretical capabilities.

16. Glossary

GATT
Generic Attribute Profile — the BLE specification defining how services and data are exposed and accessed.
OTAA / ABP
LoRaWAN activation methods — Over-The-Air Activation (dynamic session keys) versus Activation By Personalization (static, unrotated keys).
Relay attack
An attack using two colluding devices to extend the effective range of a short-range signal, defeating proximity-based security assumptions.

17. Self-Assessment

1. Why is BLE 'Just Works' pairing considered weak against an active attacker?

Just Works pairing establishes an encrypted link but doesn't authenticate the pairing exchange itself, leaving it open to interception by an active attacker present during pairing.

2. What makes NFC/RFID systems vulnerable to relay attacks despite their short intended range?

Relay attacks use two devices to extend the effective range of a short-range signal, defeating the proximity assumption the system relies on for security.
