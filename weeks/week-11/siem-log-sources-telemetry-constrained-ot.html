SIEM, Log Sources & Telemetry Pipelines for Constrained/OT Devices

Onboard non-standard OT/IoT log sources into a SIEM.

35 min read Level: MS foundation → advanced Status: Full lesson

1. Introduction

Getting OT and IoT telemetry into a SIEM sounds like a straightforward integration task until you actually try it: the protocols speak formats a typical SIEM connector has never seen, and the sheer volume of low-context device events can overwhelm normalization pipelines built for enterprise IT logs.

2. Learning Outcomes

By the end of this lesson you will be able to:

  • Onboard non-standard OT/IoT log sources into a SIEM.
  • Normalize protocol-specific telemetry (Modbus, MQTT) for correlation.

3. Prerequisites

Week 0 foundations, plus Weeks 0–10 of this course.

4. Core Concepts

OT protocol log normalization: protocols like Modbus (previewed here, detailed in Week 15) carry function codes and register addresses rather than the kind of structured, human-readable fields a SIEM connector typically expects — meaningful detection requires a normalization layer that translates "function code 6, register 40001" into something like "write single register: setpoint" before correlation rules can reason about it usefully.

SIEM onboarding for headless devices — devices with no interactive interface and no traditional syslog-style output — often requires purpose-built collectors (a gateway aggregating and forwarding on the device's behalf, per Week 7's gateway material) rather than expecting each device to speak SIEM-native log formats directly.

Retention trade-offs: Week 10's high-volume telemetry lesson noted that fleet-scale event volume can dwarf typical IT logging; SIEM retention policy for IoT/OT telemetry needs an explicit, deliberate trade-off between retention length (useful for slow-developing incidents) and storage cost, rather than defaulting to either extreme.

7. Mathematical / Formal Foundations

No formula — instead, a retention-cost trade-off framing: retaining full-fidelity telemetry for every device indefinitely is rarely affordable at fleet scale; a tiered approach (full fidelity for a short hot-storage window, aggregated/sampled data for longer cold-storage retention) is the typical practical compromise, and should be a deliberate decision rather than a storage-vendor default.

8. Practical Examples

Worked example: a building's SIEM receives raw Modbus traffic with no normalization layer. An analyst investigating an alert sees function codes and register numbers with no immediately obvious meaning, slowing investigation significantly compared to a properly normalized event reading "unauthorized setpoint write attempted on HVAC controller #14."

10. Security Perspective

Un-normalized OT telemetry doesn't just slow investigation — it can make an analyst without protocol-specific expertise unable to meaningfully triage an alert at all, effectively creating a detection blind spot even when the raw data is technically being collected.

11. Industry Perspective

OT-specific SIEM vendors and add-ons increasingly ship pre-built normalization for common industrial protocols, reducing the burden on individual organizations to build this translation layer from scratch — a maturing but still-developing area of the security tooling market.

12. Research Perspective

Research into automated protocol-aware log normalization continues to explore how to generalize this translation layer across the many proprietary and semi-proprietary protocol variants found in real industrial deployments, since full standardization across vendors remains elusive.

13. Case Study

Documented OT security assessments have repeatedly found that organizations technically collecting protocol-level logs still had effectively no detection capability, because no one had built the normalization layer needed to make that raw data analyzable — illustrating collection without normalization provides limited real security value.

14. Common Misconceptions

  • "Collecting raw protocol logs is sufficient for detection." — Without normalization into human-readable, correlatable events, raw protocol data provides limited practical detection value.
  • "All device telemetry should be retained indefinitely at full fidelity." — This is rarely affordable at fleet scale; tiered retention is the typical practical approach.
  • "Standard SIEM connectors handle OT protocols out of the box." — Many OT protocols require purpose-built normalization not included in typical enterprise-IT-focused SIEM connectors.

16. Glossary

Log normalization
The process of translating raw, protocol-specific log data into a standardized, human-readable and correlatable format.
Hot/warm/cold storage tiers
A tiered data retention strategy balancing fast access to recent data against lower-cost long-term storage.

17. Self-Assessment

1. Why is a normalization layer important when feeding OT protocol telemetry (like Modbus) into a SIEM?

Without normalization, analysts must interpret raw protocol-specific fields directly, which slows investigation and can create an effective detection blind spot even when data is technically collected.
