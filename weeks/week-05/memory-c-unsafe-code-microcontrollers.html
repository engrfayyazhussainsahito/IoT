Memory, C & Unsafe Code From First Principles on Microcontrollers

Explain memory layout differences between hosted and bare-metal C programs.

35 min read Level: MS foundation → advanced Status: Full lesson

1. Introduction

C on a microcontroller looks like C anywhere else, but the ground underneath it is different: no operating system to catch a wild pointer, often no memory protection at all, and undefined behavior that can manifest as a subtly wrong sensor reading instead of a clean crash.

2. Learning Outcomes

By the end of this lesson you will be able to:

  • Explain memory layout differences between hosted and bare-metal C programs.
  • Identify undefined behavior patterns common in firmware.

3. Prerequisites

Week 0 foundations, plus Weeks 0–4 of this course.

4. Core Concepts

A bare-metal C program's memory layout is defined by a linker script: it dictates exactly where code, initialized data, zero-initialized data, stack, and heap (if used at all) live in the chip's address space. Unlike a hosted OS, there's typically no virtual memory — these are real physical addresses, and overlap or misconfiguration in the linker script is itself a potential vulnerability.

Undefined behavior (UB) in C — signed integer overflow, use of uninitialized variables, out-of-bounds access — is dangerous everywhere, but especially so in embedded contexts where compilers aggressively optimize for tiny code size and may make assumptions based on UB that produce surprising, security-relevant behavior changes between compiler versions or optimization levels.

7. Mathematical / Formal Foundations

No formula — instead, a memory-map sanity check: sum the linker script's declared sizes for .data, .bss, heap, and maximum expected stack usage. If that sum exceeds the chip's actual RAM, you have a latent overflow condition that may only manifest under specific runtime conditions (deep call stacks, heap fragmentation) rather than immediately at boot.

8. Practical Examples

Worked example: a signed integer used to represent a sensor delta accidentally overflows under specific input conditions. Because signed integer overflow is undefined behavior in C, the compiler is free to assume it never happens — and may optimize away a bounds check that was intended to catch exactly this case, silently removing the safety net the developer thought they had written.

9. Code / Worked Example

// This bounds check can be silently optimized away by the compiler,
// because signed overflow is undefined behavior and the compiler may
// assume 'x + 10' never overflows when reasoning about this branch.
int check_range(int x) {
    if (x + 10 < x) {       // intended overflow check -- UB makes this unreliable
        return -1;
    }
    return x + 10;
}

// Safer: check using unsigned arithmetic or explicit overflow-safe patterns
int check_range_safe(int x) {
    if (x > INT_MAX - 10) {  // no UB triggered in the check itself
        return -1;
    }
    return x + 10;
}

10. Security Perspective

Undefined behavior is uniquely dangerous because it isn't a bug in the traditional sense — the compiler isn't wrong, the standard genuinely permits any behavior once UB is triggered, including silently removing a security check the developer believed was protecting them.

11. Industry Perspective

MISRA C, an industry coding standard widely used in automotive and industrial embedded development, exists largely to restrict C to a subset that avoids the most dangerous undefined-behavior patterns — adopting it (or a similar restricted subset) is a common industry mitigation.

12. Research Perspective

Compiler research into UB-detection tooling (UBSan and similar sanitizers, covered further in Lesson 5.5) has made this class of bug substantially easier to find during development than it was a decade ago, though adoption in embedded toolchains still lags behind server/desktop tooling.

13. Case Study

Multiple documented firmware bugs have traced back to compiler optimizations removing an intended safety check that relied on undefined behavior — the code "looked correct" to a human reviewer while being formally unreliable per the C standard.

14. Common Misconceptions

  • "If code compiles without warnings, it doesn't have undefined behavior." — Many UB patterns compile silently, especially at default warning levels.
  • "Undefined behavior just means 'implementation-defined, but consistent.'" — Undefined behavior can differ between compiler versions, optimization levels, or even be optimized away entirely.
  • "This only matters for very complex code." — Simple-looking overflow checks are among the most common places UB silently defeats a developer's intent.

16. Glossary

Linker script
A file specifying how code and data sections are laid out in a target's memory address space.
Undefined behavior (UB)
Program behavior for which the C standard imposes no requirements, permitting any outcome including compiler optimization that removes intended logic.
MISRA C
An industry coding standard restricting C to a safer subset, widely used in automotive and industrial embedded development.

17. Self-Assessment

1. Why can a compiler legally remove a bounds check that relies on signed integer overflow behavior?

Because signed overflow is UB, the C standard permits the compiler to assume it doesn't happen, which can lead to removal of checks written to detect that exact overflow.
