Buffer Overflows & Memory Corruption in Firmware

Explain how a buffer overflow in a protocol parser leads to control-flow hijack.

35 min read Level: MS foundation → advanced Status: Full lesson

1. Introduction

This is the lesson where a lot of this week's material converges into the classic attack: an attacker sends more data than a buffer was sized to hold, overwrites adjacent memory, and redirects program execution. On firmware, the lack of standard mitigations makes this attack far more reliable than on a modern desktop OS.

2. Learning Outcomes

By the end of this lesson you will be able to:

  • Explain how a buffer overflow in a protocol parser leads to control-flow hijack.
  • Recognize why lack of ASLR/NX changes exploitation on many MCUs.

3. Prerequisites

Week 0 foundations, plus Weeks 0–4 of this course.

4. Core Concepts

The classic anatomy: a fixed-size stack buffer receives attacker-controlled data via an unchecked copy (like strcpy or a manual loop without bounds checking). Data beyond the buffer's size overwrites adjacent stack memory — potentially including a saved return address. If the attacker controls enough of the overwritten data, they can redirect execution to code of their choosing when the function returns.

Desktop and server systems have layered mitigations against exactly this: ASLR (Address Space Layout Randomization) makes memory addresses unpredictable, and NX/DEP (No-eXecute / Data Execution Prevention) marks data memory as non-executable. Many cheap microcontrollers have neither — no MMU means no ASLR, and many have no mechanism to mark memory regions non-executable at all, making a successful overflow far more directly exploitable than the equivalent bug on a modern PC.

7. Mathematical / Formal Foundations

No formula — instead, a mitigation-availability check for your target: does the chip have an MMU (a prerequisite for meaningful ASLR)? Does the toolchain support any per-region execute-permission control? If the answer to both is no, treat every unbounded copy into a stack or heap buffer as a critical, directly exploitable finding, not a theoretical one.

8. Practical Examples

Worked example, conceptual: a network protocol parser copies an attacker-supplied field into a fixed 32-byte stack buffer using a loop with no length check. Sending a 64-byte field overflows the buffer, overwriting the saved return address with an attacker-chosen value. On a chip with no NX enforcement, the attacker's payload can even be placed in the overflowed data itself and directly executed.

9. Code / Worked Example

// Vulnerable: no bounds check on attacker-controlled length
void parse_field(uint8_t *data, uint16_t len) {
    char buf[32];
    for (uint16_t i = 0; i < len; i++) {   // len is attacker-controlled!
        buf[i] = data[i];                  // overflow if len > 32
    }
}

// Fixed: enforce the buffer's actual bound
void parse_field(uint8_t *data, uint16_t len) {
    char buf[32];
    uint16_t safe_len = (len > sizeof(buf)) ? sizeof(buf) : len;
    memcpy(buf, data, safe_len);
}

10. Security Perspective

The absence of ASLR and NX on many microcontrollers means the standard "make exploitation probabilistic and hard" mitigations desktop security relies on simply aren't available — memory safety has to be achieved through correct code and language choice (Lesson 5.4) rather than runtime mitigation.

11. Industry Perspective

Higher-end microcontrollers (Cortex-M with an MPU, or Cortex-A with a full MMU) increasingly support some subset of these mitigations, making chip selection itself a meaningful security decision for products handling untrusted network or RF input.

12. Research Perspective

Academic and industry research into lightweight control-flow integrity (CFI) schemes for constrained devices aims to provide some of ASLR/NX's protective effect without the memory and compute overhead of a full implementation — an active area given how many devices lack these protections entirely today.

13. Case Study

Numerous firmware CVEs across router, camera, and industrial-device product lines follow this exact pattern: an attacker-controlled length field, an unbounded copy, and — due to missing memory protections — a directly exploitable remote code execution vulnerability rather than a mere crash.

14. Common Misconceptions

  • "Buffer overflows are a solved problem thanks to modern mitigations." — Modern mitigations are common on desktops/servers but frequently absent on constrained microcontrollers.
  • "A crash from an overflow is the worst-case outcome." — On systems without NX/ASLR, a crash is often the mild outcome; full code execution is realistically achievable.
  • "This only affects old or poorly maintained firmware." — This bug class continues to appear in actively maintained, modern firmware releases.

16. Glossary

ASLR
Address Space Layout Randomization — a mitigation that randomizes memory addresses to make exploitation harder, requiring an MMU.
NX/DEP
No-eXecute / Data Execution Prevention — marking memory regions as non-executable to prevent injected code from running.

17. Self-Assessment

1. Why are buffer overflows often more directly exploitable on cheap microcontrollers than on modern desktop systems?

Without an MMU (for ASLR) or execute-permission control (for NX/DEP), an overflow on many microcontrollers can be exploited far more reliably than the equivalent bug on a modern desktop OS.
