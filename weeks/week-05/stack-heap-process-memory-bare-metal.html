Stack/Heap/Process Memory on Bare-Metal & RTOS Targets

Trace stack and heap usage across RTOS task switches.

35 min read Level: MS foundation → advanced Status: Full lesson

1. Introduction

On a desktop OS, the stack and heap are managed by an operating system that gives each process its own virtual address space. On an RTOS, every task typically shares one physical address space with fixed-size stacks allocated at compile time — a very different, and much less forgiving, environment.

2. Learning Outcomes

By the end of this lesson you will be able to:

  • Trace stack and heap usage across RTOS task switches.
  • Explain stack-overflow risk in a fixed-size-task-stack world.

3. Prerequisites

Week 0 foundations, plus Weeks 0–4 of this course.

4. Core Concepts

Each RTOS task gets its own stack, but its size is usually fixed at task-creation time and allocated from a shared pool of RAM. If a task's actual stack usage (determined by its deepest call chain plus any local buffers) exceeds this fixed allocation, it silently overflows into adjacent memory — which might belong to another task, or to the heap, with no OS-level page-fault mechanism to catch it the way a desktop OS would.

Static vs. dynamic allocation: many embedded style guides (and MISRA C) discourage dynamic allocation (heap/malloc) entirely in favor of static, compile-time-sized buffers — heap fragmentation on a long-running, memory-constrained device can eventually cause allocation failures that are extremely hard to reproduce and debug.

Stack canaries — a known sentinel value placed just past a buffer, checked before a function returns — are a useful mitigation but are not universally available or enabled on every embedded toolchain and architecture; verify they're actually active rather than assuming so by default.

7. Mathematical / Formal Foundations

No formula — instead, a stack-sizing exercise: measure (via static analysis tools or a stack-painting technique, filling stack memory with a known pattern and checking high-water-mark usage after running) the deepest actual stack usage for each task, and compare against its allocated size with a safety margin — not just a guessed round number.

8. Practical Examples

Worked example: a task allocates a 512-byte stack based on a rough guess. A rarely triggered error-handling code path calls three additional nested functions, each with modest local buffers, pushing actual usage to 600 bytes under that specific condition — an overflow that only manifests when that particular error path executes, making it very difficult to catch with typical testing.

9. Code / Worked Example

STACK SIZING CHECKLIST
[ ] Measured (not guessed) worst-case stack depth per task, including
    rare error-handling code paths
[ ] Safety margin added (commonly 20-25% above measured worst case)
[ ] Stack canaries/guard pages enabled if the toolchain supports them
[ ] Stack usage re-measured after any significant code change
    (a new nested function call can silently increase worst-case depth)

10. Security Perspective

A stack overflow that corrupts an adjacent task's memory is a serious, often remotely-triggerable vulnerability class — especially if the overflow can be induced by attacker-controlled input reaching a deep call chain or a rarely-tested error path.

11. Industry Perspective

Static stack-usage analysis tools that compute worst-case stack depth at compile time (rather than relying on runtime measurement alone) are increasingly integrated into embedded CI pipelines specifically to catch this class of latent bug before it ships.

12. Research Perspective

Formal worst-case stack analysis remains an active research area, particularly for codebases with function pointers or recursive calls, where static analysis tools can struggle to compute a tight, provably correct bound.

13. Case Study

A documented pattern in embedded post-mortems: a firmware update adds a new logging call deep within an existing function, incrementally increasing stack usage just enough to push a previously safely-sized task's stack into overflow territory — a regression introduced by an unrelated, seemingly minor change.

14. Common Misconceptions

  • "A stack overflow will always cause an obvious crash." — Without protection mechanisms, it can silently corrupt adjacent memory instead of crashing immediately.
  • "If the code worked in testing, stack sizing is fine." — Rare error-handling paths can have much deeper call chains than commonly tested paths.
  • "Dynamic allocation (malloc) is always fine on embedded systems if you have enough RAM." — Long-running fragmentation risk exists independent of total RAM size.

16. Glossary

Stack canary
A known sentinel value placed near a buffer, checked before function return to detect stack-based buffer overflows.
High-water-mark stack usage
The maximum stack depth actually reached by a task during execution, often measured via stack-painting techniques.

17. Self-Assessment

1. Why is a stack overflow particularly dangerous on many embedded/RTOS systems compared to a desktop OS?

Many embedded/RTOS environments lack the memory protection a desktop OS provides, so a stack overflow can silently corrupt adjacent memory rather than triggering an immediate, catchable fault.
