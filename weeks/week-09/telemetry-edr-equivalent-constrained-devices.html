Telemetry & EDR-Equivalent Monitoring for Constrained Devices

Design a minimal telemetry set that still supports detection.

35 min read Level: MS foundation → advanced Status: Full lesson

1. Introduction

This lesson answers the practical question left open by Lesson 9.1: given a minimal telemetry budget, what specific signals give the best detection value per byte transmitted, and where should the rest of the detection burden live?

2. Learning Outcomes

By the end of this lesson you will be able to:

  • Design a minimal telemetry set that still supports detection.
  • Explain trade-offs between on-device detection and network-based detection.

3. Prerequisites

Week 0 foundations, plus Weeks 0–8 of this course.

4. Core Concepts

A useful mental model: draw a line between what a device itself can meaningfully report (its own boot state, a few internal counters) versus what's better inferred from the network's external view of that device's behavior (traffic volume, destination patterns, timing) — Week 7's segmentation and RF-monitoring material.

On-device detection is cheap to transmit (a single flag or counter) but limited to what the device can observe about itself. Network-based detection can observe things the device cannot report on itself (like unexpected communication with a new external endpoint) but requires the network infrastructure — not the device — to do the analytical work.

A well-designed system uses both: on-device signals catch device-internal anomalies (unexpected reboots, firmware drift) cheaply, while network-based detection catches behavioral anomalies (unusual traffic patterns suggesting the device has been repurposed by malware) that no reasonable telemetry budget could fully capture from the device's own perspective.

No formula — instead, a coverage-gap exercise: for a given device, list the attack scenarios from Week 9's Mirai lesson (credential compromise, malware infection, propagation) and mark which detection tier (on-device or network) would actually catch each one. Gaps in this table reveal where additional investment is needed.

8. Practical Examples

Worked example: a compromised device begins scanning the internet for new victims (propagation stage). The device itself has no internal signal indicating this (from its own perspective, it's just making network connections). A network-based detection watching for an unusual volume of outbound connection attempts to diverse external IPs catches exactly the behavior the device-level telemetry would have missed entirely.

10. Security Perspective

Relying solely on on-device telemetry systematically misses exactly the behaviors most associated with active compromise (scanning, C2 communication) — network-based detection isn't optional supplementary coverage, it's often the primary detection layer for constrained devices.

11. Industry Perspective

Network-based anomaly detection appliances specifically marketed for IoT/OT environments have grown as a product category precisely because they provide detection coverage without requiring any changes to the (often unchangeable, already-deployed) device fleet itself.

12. Research Perspective

Machine-learning-based network anomaly detection for IoT traffic is an active research area, aiming to distinguish malicious behavioral patterns from the wide natural variation in legitimate device traffic without generating excessive false positives.

13. Case Study

Multiple documented fleet compromises were first detected via network-layer anomalies (unusual outbound traffic volume or destinations) rather than any signal from the devices themselves — directly validating the combined on-device-plus-network detection model this lesson recommends.

14. Common Misconceptions

  • "On-device telemetry alone is sufficient if it's well designed." — Many compromise indicators (like scanning behavior) are invisible from the device's own internal perspective.
  • "Network-based detection makes on-device telemetry unnecessary." — On-device signals like attestation catch specific compromise types (firmware tampering) that network monitoring alone can miss or only infer indirectly.
  • "This is only relevant for large enterprise deployments." — Even small deployments benefit from combining lightweight on-device signals with basic network monitoring.

16. Glossary

On-device detection
Security monitoring performed using signals a device can observe about its own internal state.
Network-based detection
Security monitoring performed by observing a device's traffic and behavior from the network's external perspective.

17. Self-Assessment

1. Why is network-based detection often essential for catching botnet-style propagation behavior in constrained devices?

A compromised device performing propagation scanning has no internal signal indicating anything is wrong from its own perspective — this behavior is only observable externally, via network-based monitoring.
