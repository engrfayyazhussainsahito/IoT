Threat Modeling for IoT/Embedded Systems

Apply STRIDE to a device, gateway, and cloud data-flow diagram.

40 min read Level: MS foundation → advanced Status: Full lesson

1. Introduction

Threat modeling is where architecture and adversarial thinking meet on paper, before a single line of firmware is written. For IoT/embedded systems, the standard STRIDE approach needs one addition to be complete: a pass for physical safety hazards that STRIDE alone doesn't ask about.

2. Learning Outcomes

By the end of this lesson you will be able to:

  • Apply STRIDE to a device, gateway, and cloud data-flow diagram.
  • Extend STRIDE with a safety-hazard pass for physical actuation.
  • Prioritize mitigations against a constrained bill of engineering hours.

3. Prerequisites

Week 0 foundations, plus Weeks 0 of this course.

4. Core Concepts

The workflow has three stages:

  1. Draw the data-flow diagram: device, gateway, broker/cloud, and user-facing app, with every trust boundary marked explicitly.
  2. Apply STRIDE at each boundary: Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege.
  3. Apply a safety-hazard pass: for every actuator or physical output, ask "what's the worst physical outcome if this command is spoofed, tampered with, delayed, or dropped?"

Step 3 is the addition this course emphasizes for CPS: STRIDE was designed for information systems and has no built-in concept of "this valve could open." A dedicated hazard pass, borrowed from safety engineering's FMEA (Failure Mode and Effects Analysis) tradition, closes that gap.

9. Code / Worked Example

STRIDE + SAFETY WORKSHEET TEMPLATE
Boundary: ____________________
[ ] Spoofing        - can an entity be impersonated here?
[ ] Tampering       - can data/commands be modified in transit or at rest?
[ ] Repudiation     - can an action be denied due to missing logs?
[ ] Info disclosure - can sensitive data leak across this boundary?
[ ] Denial of service - can this boundary be flooded or starved?
[ ] Elevation of privilege - can an entity gain more access than intended?
[ ] SAFETY HAZARD PASS - if this boundary fails in any of the above ways,
    what is the worst physical-world consequence for any actuator downstream?

10. Security Perspective

Teams that stop at STRIDE alone on a CPS system reliably miss the finding that matters most: not "can this be spoofed" but "what happens physically if it is." Adding the hazard pass as a mandatory last step catches this systematically rather than by luck.

11. Industry Perspective

Automotive (ISO 21434) and industrial (IEC 62443) security standards both require some form of combined threat/hazard analysis — this lesson's approach is a simplified, course-friendly version of what those standards mandate formally.

12. Research Perspective

Active research explores automating parts of this process — generating STRIDE candidates from architecture diagrams — but the safety-hazard pass still generally requires domain-expert judgment that's hard to fully automate.

13. Case Study

A frequently cited pattern: a threat model correctly flags "command channel lacks authentication" as a Spoofing/Tampering finding, but the accompanying risk rating treats it as a routine medium-severity access-control gap — because the model never asked what physical action the spoofed command could trigger.

14. Common Misconceptions

  • "STRIDE alone is sufficient for CPS threat modeling." — STRIDE has no built-in concept of physical safety consequence.
  • "Threat modeling is a one-time activity before launch." — It should be revisited whenever the architecture or actuator behavior changes.
  • "Only the device needs threat modeling; the cloud is someone else's problem." — Trust boundaries connect every tier; a cloud-side gap can still cause a device-side hazard.

16. Glossary

STRIDE
A threat-modeling mnemonic: Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege.
FMEA
Failure Mode and Effects Analysis — a safety-engineering method for systematically identifying failure consequences.
Trust boundary
A point in a system where data or control crosses between components with different levels of trust.
