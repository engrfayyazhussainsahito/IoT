Requirements, Abuse Cases & Secure Design for IoT Products

Write abuse cases alongside functional requirements for a device feature.

35 min read Level: MS foundation → advanced Status: Full lesson

1. Introduction

A functional requirement describes what a system should do. An abuse case describes what happens when someone tries to make it do something else. Writing both together, from the start, is one of the cheapest and most effective security investments a product team can make.

2. Learning Outcomes

By the end of this lesson you will be able to:

  • Write abuse cases alongside functional requirements for a device feature.
  • Apply secure-design patterns specific to constrained products.

3. Prerequisites

Week 0 foundations, plus Weeks 0–3 of this course.

4. Core Concepts

An abuse case follows a simple template: given an actor with some level of access, describe an action they could take that violates an intended security property, and what the consequence would be. Writing these alongside functional requirements — not as a separate, later "security review" — surfaces design flaws while they're still cheap to fix.

Secure defaults are the design-pattern payoff of this exercise: a device should ship in its most secure reasonable configuration out of the box, requiring a deliberate action to weaken security (like disabling a firewall rule), rather than requiring a deliberate action to enable it.

5. Visual Learning

graph LR

  AC --> M[Mitigation:\nauthenticated, encrypted command channel]
  M --> FR2[Updated requirement:\nincludes auth + encryption]
Every functional requirement involving a security-relevant action should get this treatment.

7. Mathematical / Formal Foundations

No formula — instead, a design-review ratio worth tracking: for every functional requirement touching authentication, authorization, or physical actuation, there should be at least one paired abuse case in the requirements document. A ratio near zero suggests abuse-case writing isn't actually happening.

8. Practical Examples

Worked example abuse case for a smart lock's "remote unlock" feature: Actor: an attacker on the same local network as the lock's gateway. Action: replay a previously captured unlock command. Consequence: unauthorized physical entry. Mitigation: include a nonce or timestamp in the command, rejected if reused or stale.

9. Code / Worked Example

ABUSE CASE TEMPLATE
Actor:          Who is attempting the abuse? (network position, access level)
Action:         What do they attempt to do?
Violated property: Confidentiality / Integrity / Availability / Safety?
Consequence:    What's the real-world impact if they succeed?
Mitigation:     What design change prevents or limits this?
Residual risk:  What remains even after the mitigation?

10. Security Perspective

Abuse cases written during requirements are dramatically cheaper to address than vulnerabilities found during a pre-launch pentest or, worse, after release — the same design flaw costs roughly an order of magnitude more to fix at each later stage of development.

11. Industry Perspective

Product teams that integrate abuse-case writing into their existing requirements process (rather than bolting on a separate "security requirements" document) see much better adoption, since it becomes part of normal product-definition work rather than an extra step engineers can skip.

12. Research Perspective

Structured abuse-case and misuse-case modeling has an established academic lineage in requirements engineering research, predating and informing modern threat-modeling practice.

13. Case Study

The replay-attack abuse case for remote-unlock features described above mirrors real, publicly documented smart-lock vulnerabilities where captured unlock signals could be replayed due to missing nonce or timestamp validation — exactly the kind of flaw this exercise is designed to catch before shipping.

14. Common Misconceptions

  • "Abuse cases are the security team's job, not product/engineering's." — Writing them alongside functional requirements works best as a shared, integrated practice.
  • "Secure defaults make a product harder to use." — Well-chosen secure defaults are usually invisible to legitimate users and only add friction for abuse attempts.
  • "If a pentest finds nothing, the abuse-case exercise wasn't necessary." — A clean pentest often reflects abuse cases having already been addressed at the design stage, not that the exercise added no value.

16. Glossary

Abuse case
A structured description of how an actor could misuse a system feature to violate a security property, paired with a functional requirement.
Secure default
A configuration a product ships with by default that favors security, requiring deliberate action to weaken rather than to enable.

17. Self-Assessment

1. What is the main benefit of writing abuse cases alongside functional requirements, rather than during a later security review?

Fixing a design-level security flaw during requirements is far cheaper than fixing it after implementation or, worse, after release.
