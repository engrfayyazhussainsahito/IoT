Authorization & Access Control on Embedded Platforms

Apply least privilege to firmware processes and services.

35 min read Level: MS foundation → advanced Status: Full lesson

1. Introduction

Authentication answers "who are you?" Authorization answers the more consequential question: "what are you allowed to do now that I know?" On embedded platforms, getting this second question wrong is how a compromised sensor process ends up able to issue actuator commands it should never touch.

2. Learning Outcomes

By the end of this lesson you will be able to:

  • Apply least privilege to firmware processes and services.
  • Design capability-scoped access for device-to-cloud commands.

3. Prerequisites

Week 0 foundations, plus Weeks 0–1 of this course.

4. Core Concepts

Two access-control models show up repeatedly:

  • RBAC (Role-Based Access Control) — permissions attached to roles (e.g., "sensor," "gateway admin"), assigned to entities. Simple to reason about, coarser-grained.
  • ABAC (Attribute-Based Access Control) — permissions computed from attributes (device type, location, time of day). More flexible, harder to audit.

Capability-based security takes a different approach entirely: instead of asking "is this identity allowed to do X," a capability is an unforgeable token that directly grants the ability to do X — possession of the capability itself is the authorization. This maps naturally onto command-scoping: a device might issue a narrowly-scoped, time-limited capability for "unlock this specific door once" rather than a broad "authenticated user can send any command" model.

Command scoping matters because embedded command interfaces are frequently more permissive than they need to be — a debug or maintenance command left reachable from the same channel as normal operation is a classic elevation-of-privilege path.

7. Mathematical / Formal Foundations

No formula — instead, a least-privilege exercise: for any command interface, count how many distinct commands a given identity or role can reach, versus how many it actually needs for its function. A large gap between those numbers is your elevation-of-privilege attack surface.

8. Practical Examples

Worked example: a gateway's maintenance API accepts both "read sensor status" (needed by the mobile app) and "flash new firmware" (needed only by the manufacturer's update service) on the same authenticated channel. A compromised mobile-app credential can now push firmware — a scope failure that proper command separation would have prevented.

9. Code / Worked Example

COMMAND SCOPE AUDIT
Endpoint/command         | Who actually needs it        | Who can currently reach it
------------------------------------------------------------------------------------
GET /status               | Mobile app, gateway            | Mobile app, gateway  (OK)
POST /flash-firmware       | Manufacturer update service    | Mobile app, gateway, update service (TOO BROAD)
POST /factory-reset         | Local physical button only     | Any authenticated network client (TOO BROAD)

10. Security Perspective

The most impactful authorization fix in many real assessments isn't adding new access controls — it's simply narrowing an overly broad existing one, like separating a "read" scope from a "flash firmware" scope that never should have shared a credential in the first place.

11. Industry Perspective

Cloud IoT platforms increasingly expose fine-grained, per-command IAM policies specifically to make this kind of scoping the default rather than something a product team has to build from scratch.

12. Research Perspective

Capability-based security has decades of operating-systems research behind it (Capsicum, seL4) and is seeing renewed interest for IoT specifically because its "possession is authorization" model maps well onto short-lived, narrowly-scoped device interactions.

13. Case Study

A widely reported smart-lock vulnerability stemmed from a maintenance command reachable over the same Bluetooth channel as normal unlock commands, with no additional scope check — allowing a nearby attacker to reach functionality that should have required physical access to a separate service port.

14. Common Misconceptions

  • "Authentication is enough; if you're logged in, you should be able to do what the app lets you do." — Authorization must independently limit actions, not just rely on the app's UI hiding options.
  • "RBAC and ABAC are mutually exclusive." — Many real systems layer coarse RBAC roles with finer ABAC conditions.
  • "Capability-based security is just RBAC with a different name." — Capabilities grant specific actions directly via unforgeable tokens, rather than checking identity against a role table each time.

16. Glossary

RBAC
Role-Based Access Control — permissions attached to roles, assigned to entities.
ABAC
Attribute-Based Access Control — permissions computed dynamically from attributes like device type or context.
Capability (security)
An unforgeable token or reference that directly grants the ability to perform a specific action.

17. Self-Assessment

1. What is the core idea behind capability-based security?

In capability-based security, holding the capability token itself is the authorization — it grants a specific action rather than relying on an identity/role lookup.
