Embedded Operating Systems & RTOS From First Principles

Explain scheduling, memory protection (or its absence), and IPC on an RTOS.

35 min read Level: MS foundation → advanced Status: Full lesson

1. Introduction

Week 0 introduced the RTOS task model at a glance. Here we go deeper: how scheduling actually decides what runs next, what memory protection buys you when it exists, and why an interrupt handler is one of the most dangerous places to have a bug on an embedded target.

2. Learning Outcomes

By the end of this lesson you will be able to:

  • Explain scheduling, memory protection (or its absence), and IPC on an RTOS.
  • Identify attack surface unique to cooperative vs. preemptive schedulers.

3. Prerequisites

Week 0 foundations, plus Weeks 0–1 of this course.

4. Core Concepts

Two scheduling philosophies dominate embedded systems: cooperative scheduling, where a task must voluntarily yield control, and preemptive scheduling, where a timer interrupt can forcibly switch tasks at any point. Preemptive scheduling (used by FreeRTOS, Zephyr) is more responsive but introduces race conditions any two tasks touching shared state must guard against with mutexes or critical sections.

Memory protection varies dramatically by chip class: high-end Cortex-A parts running embedded Linux get a full MMU with virtual memory; mid-range Cortex-M parts may have an MPU that can wall off a handful of regions; the cheapest microcontrollers have no protection at all — every task, including a compromised one, can read and write all of memory.

Interrupt Service Routines (ISRs) run outside the normal task scheduling model, often with restrictions on what they can safely call. A bug in an ISR — a buffer overflow triggered by, say, malformed sensor data arriving on a hardware interrupt — can corrupt state in ways that are unusually hard to reproduce and debug.

7. Mathematical / Formal Foundations

No formula, but a useful heuristic: assume worst-case protection unless proven otherwise. If you cannot find explicit MPU/MMU configuration in the boot code, treat every task as having full read/write access to every other task's memory.

8. Practical Examples

Worked example: a sensor-fusion task and a network task share a buffer without a mutex. Under cooperative scheduling this might work by luck (tasks only switch at defined yield points). Move the same code to a preemptive scheduler and a timer interrupt can switch mid-write, producing a race condition that only manifests intermittently — a classic embedded heisenbug.

9. Code / Worked Example

// Unsafe: shared buffer with no protection under a preemptive scheduler
uint8_t shared_buf[64];
void sensor_task(void) { memcpy(shared_buf, new_reading, 64); }   // could be preempted mid-copy
void net_task(void)    { send(shared_buf, 64); }                  // reads a torn buffer

// Safer: guard with a mutex (FreeRTOS style)
SemaphoreHandle_t buf_mutex;
void sensor_task(void) {
  xSemaphoreTake(buf_mutex, portMAX_DELAY);
  memcpy(shared_buf, new_reading, 64);
  xSemaphoreGive(buf_mutex);
}

10. Security Perspective

Race conditions in embedded code are not just reliability bugs — a torn read of a security-relevant buffer (a partially-updated session key, for instance) can leak or corrupt data in ways an attacker can sometimes trigger deliberately by flooding a device with interrupts.

11. Industry Perspective

Vendors of MPU-capable chips increasingly ship reference configurations that wall off a "secure" partition from the rest of firmware — but the security benefit only materializes if the product team actually enables and correctly configures the MPU, which is an extra step many teams skip under schedule pressure.

12. Research Perspective

Formal verification of RTOS scheduling correctness (seL4-style approaches) remains mostly confined to high-assurance systems; most commercial IoT firmware relies on testing and code review rather than formal proof of race-freedom.

13. Case Study

A documented pattern in consumer IoT firmware: a Wi-Fi credential buffer shared between the provisioning task and the connection task, with no locking, occasionally produced garbled credentials under network stress — traced eventually to a preemption race rather than a network bug.

14. Common Misconceptions

  • "An RTOS automatically prevents race conditions." — An RTOS provides tools (mutexes, queues) to prevent them, but does nothing automatically.
  • "If it works in testing, the race condition doesn't exist." — Races are often timing-dependent and can hide during testing while surfacing in the field.
  • "ISRs can safely do anything a normal task can." — Many RTOS APIs are unsafe or forbidden to call from interrupt context.

16. Glossary

MPU
Memory Protection Unit — hardware that can restrict which memory regions a task may access, without full virtual memory.
ISR
Interrupt Service Routine — code that runs in response to a hardware interrupt, outside normal task scheduling.
Race condition
A bug where the outcome depends on the relative timing of concurrent operations.

17. Self-Assessment

1. What is the key difference between cooperative and preemptive scheduling?

Preemptive scheduling can switch tasks at any time via a timer interrupt, introducing race conditions that cooperative scheduling's voluntary-yield model avoids by design.

2. Why is a shared buffer accessed by two tasks without a mutex risky under a preemptive scheduler?

Without synchronization, preemption can interleave a write and a read, producing inconsistent ('torn') data — a classic race condition.
