Embedded Linux & RTOS From Zero

Contrast general-purpose Linux with embedded Linux and RTOS design goals.

45 min read Level: MS foundation → advanced Status: Full lesson

1. Introduction

Most security intuition is built on general-purpose operating systems: multiple users, a filesystem hierarchy, and a kernel that assumes it's talking to a human at a terminal eventually. Embedded targets break almost every one of those assumptions, and the break points are exactly where security controls either exist or quietly don't.

2. Learning Outcomes

By the end of this lesson you will be able to:

  • Contrast general-purpose Linux with embedded Linux and RTOS design goals.
  • Trace the boot sequence from ROM to init on a constrained device.
  • Identify where security controls live differently on embedded targets.

3. Prerequisites

No prior lessons required — this is the course's starting point.

4. Core Concepts

Embedded Linux (Buildroot, Yocto, OpenWrt-style builds) trims a general-purpose kernel and userspace down to what a specific product needs — often a read-only root filesystem, a handful of daemons, and no interactive shell in production. An RTOS (FreeRTOS, Zephyr) goes further: no process isolation in the traditional sense, a small number of cooperating or preemptively scheduled tasks, and — on many chips — no memory protection unit separating them at all.

  • Boot sequence: boot ROM (immutable, burned at fab) → first-stage bootloader → second-stage bootloader (U-Boot, MCUboot) → kernel/scheduler → init/first task.
  • Filesystem model: read-only base image plus a small writable overlay for configuration and logs, so a factory reset is just "discard the overlay."
  • Task model: an RTOS typically runs all tasks in the same address space; a bug in one task can corrupt another's memory with no OS-level wall between them.

7. Mathematical / Formal Foundations

No formal math here, but a useful mental model: think of trust as non-increasing across the boot chain. Stage N can never grant more trust to stage N+1 than it itself was verified to have. Break that rule anywhere and the whole chain's guarantee collapses.

8. Practical Examples

On a typical embedded Linux device, / is mounted read-only from a squashfs image, while /data or /overlay is a small writable partition. A factory reset button usually just wipes that overlay partition and reboots — the base OS image never changes. Understanding this is the difference between "I patched it" and "I edited a file that will vanish on next reset."

9. Code / Worked Example

# Typical embedded Linux mount layout (inspecting from a UART shell)
$ mount
/dev/mtdblock0 on /        type squashfs (ro,relatime)
/dev/mtdblock3 on /overlay type jffs2    (rw,relatime)
overlay on /etc            type overlay (rw,...)

# Read-only root means a naive "rm -rf" of a malicious file on / will fail --
# but anything written under /overlay survives reboot and factory logic.

10. Security Perspective

Read-only rootfs is itself a security control: it limits where persistent malware can live without re-flashing the device. But it's a control that developers sometimes accidentally weaken by mounting more than necessary as read-write "for convenience" during development — and shipping that config.

11. Industry Perspective

Vendors increasingly use A/B (dual-bank) partition schemes so an OTA update writes to the inactive bank and only switches over after verification — this pattern shows up again in Week 4's OTA lesson and is one of the highest-leverage reliability-and-security investments a product team can make.

12. Research Perspective

Academic surveys of consumer IoT firmware consistently find debug shells, default credentials, or writable-by-default filesystems left over from development builds — the boot-and-filesystem model you learn here is exactly what those audits check first.

13. Case Study

A recurring firmware-audit finding: a device ships with its root filesystem mounted read-write "temporarily" for a development sprint, and the setting is never reverted before mass production. The result is a device where any code-execution bug becomes trivially persistent, because nothing stops it from writing itself to disk.

14. Common Misconceptions

  • "Read-only rootfs means the device can't be compromised persistently." — Persistence can still live in writable overlay partitions or external storage.
  • "An RTOS is just a tiny Linux." — Most RTOSes have no process isolation at all; a bug in one task can corrupt every other task's memory.
  • "Boot ROM code doesn't matter, it's just glue." — Boot ROM is usually the one stage that can never be patched after fabrication, making its bugs permanent.

16. Glossary

Boot ROM
Immutable code burned into silicon at manufacturing time; the first and most trusted link in a device's boot chain.
Overlay filesystem
A small writable layer mounted over a read-only base image, used for configuration and logs.
A/B partitioning
A dual-bank update scheme where updates write to an inactive partition before switching over.

17. Self-Assessment

1. Why do many embedded Linux devices mount their root filesystem read-only?

A read-only root filesystem constrains persistence: an attacker who can't write to / must rely on a small writable overlay, which is easier to monitor and wipe.

2. What is the key difference between an RTOS task model and a general-purpose OS process model?

Most RTOS designs skip memory protection between tasks for simplicity and speed, meaning a bug in one task can corrupt another's state.
