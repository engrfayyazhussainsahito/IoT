Python & Embedded Scripting for IoT Security

Use Python to parse serial, MQTT, and packet-capture data.

40 min read Level: MS foundation → advanced Status: Full lesson

1. Introduction

Scripting is the connective tissue of an IoT security lab: parsing serial output, talking to an MQTT broker, decoding a packet capture, and automating the boring parts of every lesson from here forward. This lesson builds the small toolkit you'll reuse constantly.

2. Learning Outcomes

By the end of this lesson you will be able to:

  • Use Python to parse serial, MQTT, and packet-capture data.
  • Write a MicroPython script that exercises a sensor safely.
  • Automate repetitive lab tasks (flashing, capture, triage) with scripts.

3. Prerequisites

No prior lessons required — this is the course's starting point.

4. Core Concepts

Three Python libraries cover most day-to-day IoT lab scripting:

  • pyserial — read and write to UART/serial devices from Python, the backbone of interacting with a debug console programmatically.
  • paho-mqtt — subscribe to and publish on MQTT topics, essential for Week 7's protocol work.
  • scapy — craft and parse network packets, useful for both Ethernet/IP traffic and, with plugins, some IoT-specific protocols.

On the device side, MicroPython lets you write Python directly on many microcontrollers, which is a fast way to exercise a sensor or peripheral safely without writing C first.

7. Mathematical / Formal Foundations

No heavy math, but a habit worth building now: always add a rate limit or timeout to any script that talks to a live device. A script with a tight retry loop and no timeout can accidentally flood a constrained device or broker — a self-inflicted denial-of-service that's entirely avoidable.

8. Practical Examples

Worked example: capturing boot output from a device over UART for later analysis, with a timeout so the script never hangs indefinitely if the device stops responding.

9. Code / Worked Example

import serial, time

PORT, BAUD, TIMEOUT_S = "/dev/ttyUSB0", 115200, 15

def capture_boot_log(path="boot_log.txt"):
    start = time.time()
    with serial.Serial(PORT, BAUD, timeout=1) as ser, open(path, "wb") as out:
        while time.time() - start < TIMEOUT_S:
            chunk = ser.read(256)
            if chunk:
                out.write(chunk)
    print(f"Captured boot log to {path}")

if __name__ == "__main__":
    capture_boot_log()

10. Security Perspective

Lab automation scripts are themselves a supply-chain surface: a script pulled from an untrusted source and run with device or network access can do real damage. Review scripts the same way you'd review any code with hardware-adjacent privileges.

11. Industry Perspective

Production device-testing pipelines use the same core idea at massive scale — automated serial/MQTT harnesses that exercise thousands of units on a factory line, just with far more tooling around results aggregation and failure triage.

12. Research Perspective

Reproducibility matters in security research: a scripted, logged capture process (rather than manual copy-paste from a terminal) is what makes a finding verifiable by someone else later.

13. Case Study

A common lab mistake: a retry loop with no backoff or timeout, written to "just keep trying" until an MQTT broker responds. Left running overnight against a real device, it can look indistinguishable from a denial-of-service attack from the device's perspective.

14. Common Misconceptions

  • "Scripts don't need error handling in a lab setting." — Unhandled errors against live hardware can leave devices or connections in a bad, sometimes unsafe, state.
  • "MicroPython is just for beginners." — It's widely used for legitimate rapid prototyping on real production-adjacent hardware.
  • "Any packet library is fine for IoT protocols." — Some IoT protocols need specialized parsing scapy doesn't support out of the box.

17. Self-Assessment

1. Why should a lab script that talks to a live device always include a timeout?

Without a timeout, a retry or read loop can run indefinitely, potentially flooding a constrained device or hanging the lab session.
