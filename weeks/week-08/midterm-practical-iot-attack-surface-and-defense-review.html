Midterm Practical: IoT Attack Surface & Defense Review

Build a device/gateway/cloud trust-boundary map for a fictional deployment.

90 min read Level: MS foundation → advanced Status: Full lesson

1. Introduction

Week 8 does not introduce new material. It checks whether the last seven weeks actually connect: can you take a fictional but realistic IoT deployment — architecture notes, a firmware image, some packet captures, a handful of logs — and produce the kind of defensible, prioritized assessment a real engineering team could act on?

2. Learning Outcomes

By the end of this lesson you will be able to:

  • Build a device/gateway/cloud trust-boundary map for a fictional deployment.
  • Identify attack surface without performing any unauthorized testing.
  • Prioritize remediation using likelihood, impact, exploitability, and safety weighting.
  • Produce a management-ready written defense plan.

3. Prerequisites

Week 0 foundations, plus Weeks 0–7 of this course.

4. Core Concepts

You'll receive a scenario packet describing a fictional smart-building deployment: door controllers, environmental sensors, a local gateway, and a cloud management platform. Your task, broken into four parts:

  1. Trust-boundary map — apply Week 1's architecture and threat-modeling skills to diagram the system and mark every boundary.
  2. Attack-surface identification — using only the provided artifacts (no live testing against real systems), list plausible attack vectors at each boundary, drawing on Weeks 2-7.
  3. Risk prioritization — score each finding using the safety-aware method from Week 1, not CVSS alone.
  4. Defense plan — propose concrete, resourced mitigations, distinguishing "must fix before launch" from "roadmap item."

7. Mathematical / Formal Foundations

Use the safety-aware scoring formula from Week 1: Risk = Likelihood (1-5) × [Digital Impact (1-5) + Safety Impact (0-5)]. Every finding in your submission needs a score using this formula — findings without a score will be returned for revision.

8. Practical Examples

Deliverable format: a written report (not a slide deck) with four sections matching the four tasks above, an evidence appendix showing your reasoning from the provided artifacts, and a one-page executive summary suitable for a non-technical stakeholder.

9. Code / Worked Example

GRADING RUBRIC (matches the assessment components below)
Asset/architecture/trust-boundary analysis .......... 15%
Attack-surface identification ....................... 20%
Risk prioritization (safety-aware scoring used) ..... 15%
Control recommendations (specific, resourced) ....... 20%
Detection and evidence plan .......................... 15%
Clarity, ethics, and report professionalism .......... 15%

10. Security Perspective

This mirrors how a real security assessment is graded internally: not on how many findings you produce, but on whether your prioritization and recommendations would actually survive contact with a resource-constrained engineering roadmap.

11. Industry Perspective

The "executive summary + evidence appendix" structure required here is the same structure used in professional penetration-test and assessment reports — this practical is deliberately training the deliverable format you'll produce professionally.

12. Research Perspective

Nothing novel is expected here — the goal is integration, not invention. Graders are specifically looking for correct application of prior weeks' frameworks, not new techniques.

13. Case Study

Past cohorts' most common deduction: treating every finding as equally severe because CVSS wasn't provided, instead of applying the safety-aware scoring method taught in Week 1. Use it explicitly.

14. Common Misconceptions

  • "This midterm requires live testing against systems." — It does not; all analysis is artifact-based, matching real pre-engagement assessment work.
  • "More findings automatically means a better grade." — Prioritization and defensibility matter more than raw count.
  • "The executive summary is optional if the technical sections are strong." — It's a graded component; technical accuracy alone isn't the full deliverable.
