Cryptography From First Principles on Resource-Constrained Hardware

Explain why algorithm choice on a microcontroller differs from a server.

35 min read Level: MS foundation → advanced Status: Full lesson

1. Introduction

Every cryptographic decision on a server assumes near-infinite CPU, RAM, and power. None of those assumptions hold on a coin-cell-powered sensor. This lesson resets your intuition for what "cheap" and "expensive" mean when the budget is measured in microjoules, not dollars.

2. Learning Outcomes

By the end of this lesson you will be able to:

  • Explain why algorithm choice on a microcontroller differs from a server.
  • Estimate the cost of common primitives on a Cortex-M class chip.

3. Prerequisites

Week 0 foundations, plus Weeks 0–2 of this course.

4. Core Concepts

Three budgets shape every cryptographic choice on constrained hardware:

  • Compute budget — a Cortex-M0 core has no floating point and limited instruction throughput; public-key operations that take microseconds on a server can take hundreds of milliseconds here.
  • Memory budget — some microcontrollers have as little as a few kilobytes of RAM; an algorithm's working-memory footprint can rule it out entirely, independent of CPU cost.
  • Power budget — every CPU cycle costs energy; on a battery-powered device, cryptographic overhead directly subtracts from battery life, sometimes measured in years.

Hardware crypto accelerators (AES engines, true random number generators built into silicon) can shift this calculus dramatically — an operation that's prohibitively expensive in software can become nearly free with dedicated hardware support, which is why chip selection is itself a security-relevant engineering decision.

Constant-time implementation — ensuring an operation takes the same time regardless of secret data — matters even more on constrained devices, where a simpler, more easily side-channel-observable implementation is often the default choice under resource pressure.

7. Mathematical / Formal Foundations

A rough energy-cost comparison often cited in embedded crypto literature: an ECC point multiplication can cost on the order of 10-100x the energy of a symmetric AES-CCM operation on the same constrained hardware. This asymmetry is exactly why protocols minimize how often public-key operations occur (see Week 3's later lessons on session design).

8. Practical Examples

Worked example: choosing between software AES and a hardware AES peripheral on a microcontroller that has one. The hardware peripheral typically completes an encryption operation in a fraction of the CPU cycles and energy of a software implementation, and — as a side benefit — is far less likely to have timing variations tied to the key, since the hardware implementation is usually constant-time by design.

10. Security Perspective

Resource pressure is a common root cause of weakened cryptography in the field — a team facing a tight power budget may reach for a smaller key size or a home-rolled lightweight scheme rather than a vetted lightweight standard, trading security margin for a power win that a hardware accelerator or protocol-level optimization could have provided more safely.

11. Industry Perspective

Silicon vendors increasingly market "security-enabled" microcontroller lines specifically featuring hardware crypto accelerators and secure key storage as a differentiator — chip selection has become a genuine security architecture decision, not just a cost/performance one.

12. Research Perspective

The NIST Lightweight Cryptography project (covered in the next lesson) exists precisely because this budget problem is real and widespread enough to warrant standardizing new primitives rather than leaving every vendor to improvise its own trade-offs.

13. Case Study

Multiple documented cases show battery-life pressure leading product teams to disable or weaken TLS certificate validation, or to skip encryption on "less sensitive" telemetry entirely, as a power optimization — illustrating how budget constraints can erode security if not addressed with the right primitive choices from the start.

14. Common Misconceptions

  • "The most secure algorithm on paper is always the right choice." — On constrained hardware, an algorithm that can't fit the power/memory budget may get bypassed or weakened entirely, which is worse.
  • "Hardware acceleration means you don't need to think about crypto choices." — You still need to select and correctly use the right primitive; hardware just changes the cost calculus.
  • "Constant-time coding only matters for servers facing network attackers." — Physical or local-network attackers can exploit timing side-channels on embedded devices too (see Week 6).

16. Glossary

Hardware crypto accelerator
A dedicated hardware block that performs cryptographic operations (e.g., AES, SHA) far more efficiently than general-purpose software.
Constant-time implementation
Code written so its execution time does not depend on secret data, preventing timing side-channel leaks.

17. Self-Assessment

1. Why might a resource-constrained device use a hardware crypto accelerator instead of a software implementation?

Hardware accelerators generally cost far less energy and compute than software equivalents, and often avoid timing side-channels inherent to naive software implementations.
