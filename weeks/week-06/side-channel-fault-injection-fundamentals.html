Side-Channel & Fault-Injection Fundamentals (power analysis, glitching)

Explain the principle behind simple power analysis at a conceptual level.

35 min read Level: MS foundation → advanced Status: Full lesson

1. Introduction

Even a device with a flawless boot chain and a well-locked debug port can leak its secrets through channels that have nothing to do with logical access at all: the power it draws, the time it takes, or what happens if you deliberately make it misbehave for a few nanoseconds at exactly the right moment.

2. Learning Outcomes

By the end of this lesson you will be able to:

  • Explain the principle behind simple power analysis at a conceptual level.
  • Describe how voltage/clock glitching can skip a security check.

3. Prerequisites

Week 0 foundations, plus Weeks 0–5 of this course.

4. Core Concepts

Power analysis exploits the fact that a chip's power consumption correlates with the data it's processing. Simple Power Analysis (SPA) looks for visually distinguishable patterns in a single power trace (for example, spotting the different number of rounds in an RSA operation depending on a key bit). Differential Power Analysis (DPA) is more powerful: it statistically combines many traces to extract key bits even when no single trace shows an obvious pattern, defeating many naive implementations that "look" constant-time but leak statistically.

Fault injection deliberately induces a hardware fault — a brief voltage drop, an out-of-spec clock pulse, a targeted laser pulse — timed to corrupt a single instruction or comparison. A classic target: skipping the branch instruction that checks "is this password correct" or "is this signature valid," causing the check to pass regardless of the actual input.

These are not purely theoretical: both technique families have moved from academic research into commercially available tooling, meaning the required sophistication has dropped substantially over the past decade.

7. Mathematical / Formal Foundations

No formula — instead, a conceptual takeaway: DPA's power comes from averaging out random noise across many traces while a signal correlated with a secret key bit remains consistent — meaning it isn't defeated by a chip merely being "noisy," only by genuine constant-time, constant-power-profile design or dedicated hardware countermeasures (masking, shielding).

8. Practical Examples

Worked example, conceptual: a device compares a user-supplied PIN to a stored value using a simple loop that exits early on the first mismatched digit. This creates a timing (and potentially power) signature correlated with how many leading digits were correct — an attacker can incrementally guess the PIN one digit at a time rather than brute-forcing the whole space, entirely through a side channel rather than breaking any cryptography directly.

9. Code / Worked Example

// Vulnerable: early-exit comparison leaks timing information
int check_pin(const char *input, const char *stored, int len) {
    for (int i = 0; i < len; i++) {
        if (input[i] != stored[i]) return 0;   // exits early -- timing leak
    }
    return 1;
}

// Safer: constant-time comparison, always examines every byte
int check_pin_constant_time(const char *input, const char *stored, int len) {
    int diff = 0;
    for (int i = 0; i < len; i++) {
        diff |= (input[i] ^ stored[i]);   // no early exit, no data-dependent branch
    }
    return diff == 0;
}

10. Security Perspective

Side-channel and fault-injection resistance can't be bolted on after the fact the way a firmware patch can — it typically requires re-designing the specific comparison, computation, or hardware layout involved, which is why threat-modeling for these attack classes needs to happen early, especially for any device handling authentication or key material.

11. Industry Perspective

Payment card and secure-element certification schemes (Common Criteria, EMVCo) mandate specific, audited testing against both power-analysis and fault-injection attack classes — a recognition that commercial-grade tooling has made these attacks practical enough to require formal defense.

12. Research Perspective

Side-channel research continues to find new leakage sources in increasingly complex systems (cache-timing side channels in higher-end SoCs, electromagnetic emanation analysis) — this remains one of the most active subfields in hardware security research.

13. Case Study

Fault-injection techniques have been used in documented research to bypass secure-boot signature checks and debug lockouts alike on commercial devices, underscoring that these aren't purely academic concerns for products with a meaningful threat model that includes a well-resourced physical attacker.

14. Common Misconceptions

  • "Side-channel attacks require nation-state-level resources." — Commercially available tooling has substantially lowered the barrier to entry for many of these techniques.
  • "Constant-time code alone defeats all side-channel attacks." — It defeats timing side channels specifically; power and electromagnetic side channels require additional hardware-level countermeasures.
  • "If my code has no secret-dependent branches, it's automatically DPA-resistant." — DPA can extract information even from code without explicit secret-dependent branches, since power consumption correlates with the actual data values being processed, not just control flow.

16. Glossary

Side-channel attack
An attack that extracts secret information from a system's physical characteristics (timing, power, electromagnetic emissions) rather than breaking its logic or cryptography directly.
Fault injection
Deliberately inducing a hardware fault (voltage glitch, clock glitch, laser pulse) to corrupt execution at a targeted moment.
Constant-time implementation
Code designed so execution time (and ideally power profile) does not depend on secret data.

17. Self-Assessment

1. What does Differential Power Analysis (DPA) exploit that Simple Power Analysis (SPA) alone often cannot?

DPA's strength comes from statistically analyzing many traces to find correlations with secret data, succeeding even where a single trace (SPA's approach) shows nothing conclusive.

2. What is the general goal of a fault-injection attack against a security check?

Fault injection typically aims to corrupt a specific instruction or comparison at a precise moment, such as causing a security check to erroneously pass.
