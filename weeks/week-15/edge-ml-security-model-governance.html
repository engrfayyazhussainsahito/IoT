AI at the Edge: Edge-ML Security & Model Governance

Identify attack surface introduced by on-device ML models.

35 min read Level: MS foundation → advanced Status: Full lesson

1. Introduction

As machine learning models move from the cloud onto the edge device itself — for latency, privacy, or bandwidth reasons echoing Week 14's data-minimization material — they bring an entirely new category of attack surface that this course hasn't yet directly addressed: attacks against the model itself, not just the software running it.

2. Learning Outcomes

By the end of this lesson you will be able to:

  • Identify attack surface introduced by on-device ML models.
  • Apply model-governance practices to models deployed on constrained hardware.

3. Prerequisites

Week 0 foundations, plus Weeks 0–14 of this course.

4. Core Concepts

Model extraction and inversion risk: an attacker with access to a deployed edge model (via the device's normal inference interface, or via physical extraction per Week 6's hardware techniques) may be able to reconstruct a close approximation of the model itself (extraction) or infer sensitive information about the data it was trained on (inversion) — risks that don't exist for traditional software logic in the same way.

Adversarial input risk for edge sensors means crafting physical-world inputs (a specially patterned sticker on a stop sign, for a vision model; a specific acoustic pattern, for an audio model) designed to cause a model to misclassify — a physical-world analog to the input-validation concerns from Week 4, but targeting the model's learned behavior rather than a traditional parser's logic.

Model update governance extends Week 4's OTA integrity material to model weights specifically: a model update needs the same signed, verified delivery as firmware, since a maliciously modified model could be tuned to fail in specific, attacker-chosen ways without the deployed system otherwise showing any obvious sign of compromise.

7. Mathematical / Formal Foundations

No formula — instead, a threat-surface question specific to ML: for a given edge model, what real-world physical input could an attacker plausibly craft and place in the model's field of sensing (camera view, microphone range, sensor input) to trigger a misclassification, and what real-world consequence would that misclassification have?

8. Practical Examples

Worked example: an edge-deployed computer-vision model for an industrial safety system is evaluated for adversarial robustness by testing whether small, physically realistic perturbations (dirt, stickers, lighting changes) could cause it to fail to detect a safety-relevant condition — treating this as a safety-critical testing requirement (echoing Week 1's safety-first framing) rather than purely an ML performance metric.

10. Security Perspective

Edge ML security requires threat-modeling the model itself as a distinct asset, not just the code running around it — a perfectly secure software implementation can still ship a model with serious extraction, inversion, or adversarial-robustness weaknesses that traditional application security review wouldn't catch.

11. Industry Perspective

Organizations deploying safety-relevant edge ML (autonomous systems, industrial vision systems) increasingly treat adversarial robustness testing as a required pre-deployment gate, similar in spirit to the fuzzing requirement from Week 5 for traditional firmware.

12. Research Perspective

Adversarial machine learning remains a highly active research area, with an ongoing back-and-forth between new attack techniques and new defensive/robustness methods — practitioners should expect this to remain a moving target rather than a solved problem for the foreseeable future.

13. Case Study

Published research has repeatedly demonstrated successful adversarial attacks against real-world deployed vision systems using physically realizable perturbations (not just digital, pixel-level manipulation), directly validating the practical, not just theoretical, nature of this risk category.

14. Common Misconceptions

  • "Edge ML security is just standard software/firmware security applied to a model file." — Model extraction, inversion, and adversarial input are distinct attack categories targeting the model's learned behavior specifically.
  • "Adversarial attacks only work in controlled digital/pixel-level scenarios, not the real physical world." — Physically realizable adversarial perturbations have been repeatedly demonstrated in research against real deployed systems.
  • "Model updates don't need the same integrity protection as firmware updates." — A maliciously modified model can be tuned to fail in specific, attacker-chosen ways, warranting the same signed-update rigor as firmware.

16. Glossary

Model extraction
An attack that attempts to reconstruct a deployed machine learning model's parameters or behavior through repeated querying.
Adversarial input
A specially crafted input designed to cause a machine learning model to misclassify or behave incorrectly.

17. Self-Assessment

1. What distinguishes an 'adversarial input' attack against an edge ML model from a typical software input-validation vulnerability?

Adversarial inputs specifically target a model's learned decision boundaries to cause misclassification, a fundamentally different attack surface than traditional software parsing or logic vulnerabilities.
